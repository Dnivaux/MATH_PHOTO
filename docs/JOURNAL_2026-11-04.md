supprimé), alias rangés, empreintes SHA-256 et tailles ajoutées aux versions GGUF.

## 3. Le choix du modèle OCR embarqué

### Six modèles sur le même banc
300 images synthétiques « façon photo » (polices variées, perspective, flou, bruit, ombres) :

| Modèle | Licence | Formules justes | Limites | Temps (CPU) |
|---|---|---|---|---|
| pix2tex (dans l'app au départ) | MIT | 17,3 % | 22,7 % | 350 ms |
| PP-FormulaNet+-S | Apache | 21,7 % | 27,3 % | 211 ms |
| PP-FormulaNet-S | Apache | 29,0 % | 37,9 % | 190 ms |
| **pix2text-mfr** | MIT | **95,7 %** | 98,5 % | 197 ms |
| **pix2text-mfr 1.5** | MIT | 89,7 % | **100 %** | 224 ms |
| TexTeller (serveur, GPU) | Apache | 89,3 % | 92,4 % | 155 ms |

Écartés sans mesure : Texo (licence AGPL, incompatible avec l'app), UniMERNet-tiny (441 Mo).

### Le bug du banc qui aurait faussé la décision
Avant correction, pix2text-mfr était à **0 % sur les limites** et TexTeller à 70 %. Les modèles écrivaient
juste, mais autrement : `\operatorname*{l i m}`, `\underset{x\to 0}{\lim}`, `\mathrm{s i n}`, formule encadrée
par `\boxed{…}`. Une mise en forme commune (`serving/ocr/text.py`), appliquée à tous les modèles et au serveur,
a corrigé le banc. **Sans elle, on aurait écarté le meilleur modèle pour une question d'écriture.** Les anciens runs
sont tagués `invalid`.

### Deux lecteurs qui votent
Les deux pix2text-mfr ne se trompent pas sur les mêmes images. L'app compare leurs lectures à l'écriture près
(sans espaces, `\left`/`\right` ni accolades de regroupement) :
- **accord sur 267 images sur 300, et toutes ces lectures sont justes** ;
- en cas de désaccord, le serveur relit la photo ; hors connexion, l'utilisateur choisit entre les deux lectures.

### Quantization (grille embarqué niveau 2)

| pix2text-mfr | Taille | Formules justes | Temps |
|---|---|---|---|
| FP32 | 118 Mo | 95,3 % | 188 ms |
| FP16 | 59 Mo | 95,3 % | 205 ms |
| **INT8 dynamique (déployé)** | **32 Mo** | **95,7 %** | **85 ms** |

INT8 : **3,7 fois plus petit, 2,2 fois plus rapide, sans perte**. FP16 n'apporte rien sur CPU et ne tourne pas en
WASM. (Pour la version 1.5, l'INT8 coûte 2 points.)

### Intégration et vérifications
- Export reproductible au bit près (`clients/mobile/scripts/p2t_mfr/export.py`, révisions figées, SHA-256).
- Implémentation de référence en Python **identique à transformers sur 20 images sur 20**.
- Moteur JavaScript de l'app réécrit, validé dans Chromium face à Python (`npm run harness`) : **22/24 lectures
  identiques au caractère près, 24/24 même formule**.
- Les 600 lectures justes du banc sont toutes comprises par le moteur de calcul de l'app, avec le bon type.
- Sur les photos de test du collègue, là où pix2tex produisait du charabia, les deux lecteurs lisent juste.

### Ce que le téléphone a montré
Sur des **photos d'écran**, le moiré et des bouts de lignes voisines dans le cadre font douter les lecteurs et
déclenchent la relecture serveur (5 à 10 s). Pistes notées : lisser l'image, effacer ce qui touche le bord du
cadre, relire sur le serveur en parallèle du second lecteur. Sur papier, cas d'usage réel, le moiré disparaît.

## 4. Après-midi : les outils MLOps

### Test de charge (grille MLOps 2), `make load-test`
Locust simule des téléphones (8 résolutions pour 1 relecture OCR et 1 vérification de modèle, 1 à 3 s entre deux
requêtes), par paliers, un run MLflow par palier.

| Utilisateurs simultanés | Avant | Après correction |
|---|---|---|
| 32 | 9,1 req/s, p95 3,1 s | 10,5 req/s, p95 1,6 s |
| 64 | 5,9 req/s, p95 13,3 s | **16,6 req/s, p95 1,7 s** |
| 128 | 5,5 req/s, p95 27,6 s | 22,9 req/s, p95 3,1 s |

**Deux goulots trouvés et corrigés**, avec `docker stats` et les étapes mesurées par Prometheus :
1. **Le bac à sable** était limité à 2 cœurs et saturait (un Python + SymPy par exécution) → 8 cœurs.
2. **L'OCR serveur** (une photo à la fois sur CPU) bloquait les fils de la gateway, au point de ralentir les
   requêtes les plus simples → appel asynchrone : les résolutions ne l'attendent plus.

> Message pour la soutenance : un débit qui **baisse** quand la charge monte n'est pas le GPU ; il faut mesurer
> chaque étape. Capacité : **64 utilisateurs simultanés sans échec**. Prochain goulot : l'OCR serveur, puis le GPU.

### Détection de dérive (grille MLOps 2), `make drift`
- La gateway garde pour chaque résolution les caractéristiques de la formule (longueur, variables, fractions,
  puissance, fonctions), **jamais la formule elle-même** ; même calcul sur les données d'entraînement.
- Evidently compare : (1) les formules reçues aux données d'entraînement ; (2) la fenêtre courante à la précédente
  (types, raisons d'escalade, statuts, latence).

| Scénario | Résultat |
|---|---|
| Trafic normal | **aucune dérive** (6 colonnes sous le seuil) |
| Trafic de limites seulement | **dérive sur 6 colonnes sur 6** |
| Charge passée de 64 à 128 utilisateurs | seule la latence dérive : juste |

Bug corrigé en route : sur de gros échantillons, Evidently donne une distance (dérive si grande), pas une p-value
(dérive si petite).

### VM et déploiement automatique (grille MLOps 1 et 2) : écrits, à lancer
- `infra/terraform` (OpenTofu + KVM) : VM Ubuntu 24.04, Docker, stack sans GPU, runner GitHub auto-hébergé.
- `.github/workflows/deploy.yml` : après une CI verte sur `master`, déploie le commit testé, vérifie (santé + une
  résolution) et **revient au commit précédent si la vérification échoue**.
- La production reste sur l'hôte (GPU) : pas de passthrough GPU vers la VM, comme prévu au dossier.
